# Character art: getting a rigged model into the game

Everything in Nagori is generated by code, and the people are no exception:
`buildHuman` makes the player and every pedestrian out of lofts and sculpted
surfaces. That is the shipping geometry until commissioned art replaces it.

This is the route the art takes when it arrives.

## The seam

`Character` looks for `public/assets/characters/<model>.glb`. If it is there
and its skeleton carries the joints the animation drives, the character *is*
that model; if it is not, the character is the generated body. Nothing else in
the game changes either way — not the controller, not the animation states,
not the scenes that place characters.

Which model a person uses is `spec.model`, which is deliberately not
`spec.name`: a name identifies an individual (`cook.ramen_iroha`,
`citizen7`), a model identifies a file that any number of people can be
built from.

```ts
// src/player/rig/CharacterSpec.ts
export function aikoSpec(): CharacterSpec {
  return { name: "aiko", model: "aiko", height: 1.63, /* … */ };
}
```

Regions preload with `Character.preload(scene, assets, ["aiko"])`, the same
shape as the asset catalog's `prepare`, because characters are built
synchronously in the middle of laying out a room and cannot fetch there.

## What the game needs of a model

Two things.

**A skin.** A glTF `skins` entry with joints and weights. A model with bones
and no weights loads and then does not deform — and the commonest way to
produce one is to merge UniRig's *skeleton* output instead of its *skinning*
output.

**Bones it can name.** The animation drives seventeen joints:

```
hips  spine  chest  neck  head
shoulderL/R  elbowL/R  wristL/R
thighL/R  kneeL/R  ankleL/R
```

`src/player/rig/BoneNames.ts` maps a model's own names onto those. It knows
Mixamo (`mixamorig:LeftArm`), VRoid/VRM (`J_Bip_L_UpperArm`) and Blender or
Rigify (`upper_arm.L`), and it reports anything it cannot place rather than
guessing. If your rig uses another convention, add it there — that file is the
contract, and `tests/bone-names.test.mjs` is where it is held to it.

> **The trap.** In both Mixamo and VRM, `Shoulder` is the *clavicle*;
> `UpperArm`/`Arm` is the joint the arm actually swings about. Our `shoulderL`
> is the latter. Bind the name rather than the joint and every arm animation
> lands on the collarbone, and the arms barely move. The matcher handles this;
> it is written down because anyone extending it will meet it.

Check any model before wiring it in:

```bash
node --experimental-strip-types tools/check-rig.mjs path/to/model.glb
```

It prints a line per joint and exits non-zero if any is unbound.

## Rigging a mesh that has no skeleton

If the mesh arrives unrigged, [UniRig](https://github.com/VAST-AI-Research/UniRig)
(SIGGRAPH '25, MIT licence) predicts a skeleton and skinning weights for it.
It does **not** model anything — the mesh is yours to supply, and no amount of
rigging will change how a mesh looks.

```bash
git clone https://github.com/VAST-AI-Research/UniRig ~/UniRig
# then follow that repository's README for PyTorch, spconv and flash_attn

tools/rig-character.sh ~/art/aiko.glb aiko
```

That runs UniRig's three documented stages — skeleton, skinning, merge — and
writes `public/assets/characters/aiko.glb`, then checks the bones with
`check-rig.mjs`.

**Requirements, none of which are optional:** a CUDA GPU, Python 3.11 with
PyTorch, and network access to Hugging Face, which is where the checkpoint is
fetched from on first run.

> `rig-character.sh` has never been run end to end. It was written in a
> sandbox with no GPU, no PyTorch and no route to Hugging Face, so it wraps
> commands taken from UniRig's README and checks its ground carefully, but the
> first person to run it should expect to debug UniRig's own installation.
> What *has* been tested is the part either side of it: `tests/` builds a real
> .glb container and takes it through the same parser and the same matcher the
> game uses.

If the skeleton comes out wrong, fix it before skinning — upstream is explicit
that skinning degrades badly on a poor skeleton, and `--seed` gives a
different prediction to try.

## Where this does not help

UniRig rigs; it does not model. Reaching the look of a modern commercial game
needs sculpted, textured, skinned character art, and that is an art problem
rather than a code one. What this pipeline buys is that when such a model
exists, it is one command and one file drop away from being in the game —
and that the generated body stands in until then.
